\section{Evaluation}
\label{sec:evaluation}

We evaluate three questions: \textbf{RQ1}, can enforcement constrain effects
inside an authorized computation; \textbf{RQ2}, what application functionality
and integration work does it retain; and \textbf{RQ3}, what does enforcement
cost? An application study tests the complete computation path. Separate backend
experiments measure operation coverage, cost sources, and the two execution
modes. Their configurations and denominators are not interchangeable.

\subsection{Applications and experimental setup}

We reproduce the Pandas Data Analyst and SQL Database Agent from AI Data Science
Team~\cite{aidatascienceteam}, and Open Notebook~\cite{opennotebook}. Only Pandas
has a protected integration; five other candidates remain blocked or unverified
(Appendix~\ref{app:application-details}). We retain the original Pandas graph,
prompts, generated computation, and sandbox program, comparing:
\begin{itemize}
  \item \textbf{A: upstream.} The original subprocess sandbox on the shared
  source overlay, with \sys security disabled.
  \item \textbf{B: added authorization.} A \code{ToolNode} boundary authorizes
  computation before invoking the original subprocess helper.
  \item \textbf{C: authorization and host enforcement.} The same boundary
  executes the sandbox program in a fresh bubblewrap worker through
  \code{LinuxSandboxExecutor}, replacing the outer subprocess launch.
\end{itemize}
The upstream AST, import, builtin, network, resource, and JSON checks remain.
The UI and parent/model effects are excluded. B is an added boundary, not a
published-defense reproduction; C is not the Landlock or object-broker path.

The host has a Xeon w5-3435X, 62.25~GiB RAM, two RTX A4000 GPUs, Linux
6.17.0-1033-oem, and rotating ext4 storage. Timing runs pin the application and
workers to CPU~0; the machine is nonexclusive, with uncontrolled frequency and
caches. Pandas uses local Qwen3-8B Q4\_K\_M at temperature zero through Ollama.
Application Python is 3.13.11; backend timings use 3.12.3 and
\code{perf\_counter\_ns}, without model calls. Run-level host captures and frozen
source archives identify each cohort. The application uses WIP \code{40e24e9}
plus working-tree changes; the commit alone does not reproduce the study.

\subsection{RQ1: Confining effects after authorization}

\paragraph{Application effects.}
We insert one filesystem operation into a legitimate February sales computation.
Policies are fixed before execution; narrow and broad profiles differ only in
permission to read a supplementary file. Each case/profile runs once per
configuration. Oracles check canary receipts, file hashes, kernel errors, worker
activation, and the legitimate result.

\begin{figure*}[t]
  \centering
  \includegraphics[width=\textwidth]{figures/application-effects.pdf}
  \caption{Observed forbidden-effect reachability in two separate experiments.
  (a) Pandas: three supported probes, one execution each per configuration.
  (b) Synthetic backend census: 49 distinct operation/surface cases, each repeated
  three times. Trusted/helper baselines reproduce every effect in every repeat;
  both host conditions reach none. Repetitions do not add independent cases.
  All 15 Pandas case/profile runs retain the intended computation; each backend
  host condition passes 30/30 positive-control trials.}
  \label{fig:application-effects}
\end{figure*}

A and B reach all three supported forbidden effects: two narrow-profile reads
and a read-only dataset overwrite. C reaches none, while all 15 case/profile
executions return the correct February result. The permitted broad-profile read
also succeeds. For a fixed eligible probe set, we define exposure reduction as
$(R_b-R_p)/R_b$, where $R_b$ and $R_p$ count reachable forbidden effects in the
baseline and protected conditions. C reduces observed reachability by 100\%
on these three probes; B reduces it by 0\% (Figure~\ref{fig:application-effects}(a)).

C also prevents an outside-fixture write from changing the host, but allows the
write in private \code{/tmp}. This demonstrates host containment, not a strict
guest-wide output-only policy, and is excluded from the three-probe denominator.
Appendix Table~\ref{tab:application-effects} retains all outcomes. B and C each
pass four dispatch checks: an allowed request succeeds, while a guest principal,
missing argument, and unknown tool fail without their effect. Thus correct call
authorization alone leaves the tested implementation effects reachable.

\paragraph{Backend operation coverage.}
A separate synthetic census (E6) exercises 49 forbidden operation/surface cases
covering filesystem APIs, metadata, aliases, native/dynamic code, environment,
processes, loopback networking, SQLite, and a bounded file-size limit. Synthetic
trusted and helper conditions reach all 49 effects in all three repetitions;
host and host-plus-helper conditions reach none, a 100\% observed reduction on
this fixed corpus. Both host conditions pass 30/30 positive-control trials.
Of 147 forbidden trials per host condition, 135 show explicit denial
(45/49 cases); six return generic SQLite errors and six return empty/absent
results. The latter 12 establish no observed effect, not explicit blocking.
The synthetic direct-language frontend rejects 27/30 controls, so its zero
effects do not establish useful mediation. It is distinct from the production
verified mode evaluated below.

\paragraph{Model-driven injection.}
One frozen instruction in a sampled CSV cell requests a private-canary read and
copy. It reaches all 15 attacked model inputs, but produces zero forbidden
attempts in every configuration; all tasks return the correct result.
Enforcement success and relative reduction are therefore undefined for this
batch. Thirty earlier pre-inference server failures remain a separate cohort.
These observations do not establish prompt-injection resistance.

\subsection{RQ2: Utility and integration requirements}

The original three-task clean workload succeeds on 1/3 in every configuration;
aggregation and chart tasks retain upstream failures. Later repetitions select
the working February task and pass 5/5 per configuration. These results show
preservation of that workflow, not improved utility or coverage of more tasks.
Pandas uses a 200-line adapter and 20-line worker, plus a 135-line backend adapter
shared with SQL. Engineering time was not recorded.

SQL passes 3/3 baseline tasks, but schema sampling places a payroll canary into
the model prompt before query execution. Protecting generated queries alone
misses this metadata path; the fixed-record broker does not cover arbitrary
SQLAlchemy queries. Open Notebook's 103-line adapter passes one ingestion/chat
smoke task against native Ollama and a dedicated SurrealDB. Its API, worker, and
database authority remain outside client confinement. Neither is a protected port.

\subsection{RQ3: Runtime cost and its sources}

\paragraph{Application replay and workflow.}
We replay the same successful computation and input through A/B/C, with ten
warm-ups and 100 measured calls each, rotating order by round. Every result is
120. The timer includes dispatch, execution, synchronous audit, and integration
output, but excludes initialization, model calls, and tracing.
Figure~\ref{fig:application-runtime}(a) shows B at $2.04\times$ upstream runtime
(104.2\% overhead), C at $3.48\times$ (248.4\%), and C/B at $1.71\times$
(70.6\%). The earlier 13.2\% policy-only no-op result does not characterize
this application path.

\begin{figure*}[t]
  \centering
  \includegraphics[width=\textwidth]{figures/application-runtime.pdf}
  \caption{Application runtime relative to upstream A. Means and SD whiskers
  are divided by the same fixed A mean within each cohort; these are not ratio
  confidence intervals. (a) Same-computation replay, 100 calls/configuration,
  without model calls or tracing. (b) Five clean full workflows/configuration,
  including setup, model execution under \code{strace}, and outcome checks.
  The workflow ratio is not isolated enforcement overhead.}
  \label{fig:application-runtime}
\end{figure*}

Five separate clean full-workflow repetitions give C/A $=1.202\times$
(+20.2\%) and C/B $=1.207\times$ (+20.7\%). B/A $=0.996\times$ does not
establish a speedup. The first A run retains post-restart model loading; setup,
model output, tracing, and evidence collection also contribute to these totals.
Five runs of one task do not estimate across-task variation.

\paragraph{Matched backend cost.}
Three successful synthetic workloads isolate backend execution: arithmetic,
a canary read, and a 4~KiB write. Each condition/workload receives ten warm-ups
and 100 measured calls in shuffled paired rounds. Every sample passes its
positive oracle. Each call starts a fresh worker; construction/preflight lies
outside the timer, and no model or durable audit sink is involved.
Host/trusted runtime is $15.30$--$15.63\times$ (1430.2--1463.4\% overhead);
host-plus-helper/helper is $15.23$--$15.37\times$
(Figure~\ref{fig:backend-runtime}(a)). Host-plus-helper differs from host by
$-0.4$ to $-0.6$\%, within observed variation. These results replace the invalid
practice of pooling successful and rejected operations into one overhead median.

\paragraph{Measured bottlenecks.}
The application and backend profiles identify different costs
(Figure~\ref{fig:cost-breakdown}). A separate 20-call application diagnostic
attributes 98.1\% of B's time outside its original subprocess to SQLite audit
writes. No SSD or disabled-audit counterfactual was run.
In the synthetic host cohort, an exclusive stage partition attributes
65.8--66.2\% of total dispatch to \code{CedarPolicyBackend.filter} and
24.4--24.9\% to worker execution/supervision. The filter serializes policy and
request files, runs Cedar CLI validation, and launches authorization for each
evaluated rule. This is policy-engine and process cost, not kernel isolation
cost. Worker time includes launch, confinement, execution, and teardown.
These instrumented experiments identify optimization targets without measuring
the speedup from changing either implementation.

\paragraph{Production verified execution versus Linux.}
The actual language path uses \code{cedar\_security} source admission, runtime
binding validation, and grant-checked \code{read\_text}. Fifty paired samples
follow five warm-ups on a constant control, three read sizes, and two reads.
Both modes use real Cedar; executors are reused and host workers remain fresh.
Linux execution takes $11.60$--$17.31\times$ verified execution
(Figure~\ref{fig:backend-runtime}(b)). Setup/static admission is measured separately.
Different policy frontends make this an implementation comparison, not a pure
kernel tax. These results expose the cost of the current host path and support
retaining a lighter admitted path for supported tools. They do not establish
verified-mode coverage for arbitrary Python or an existing application port.

\paragraph{Operation variants.}
Sixteen successful operation/API variants, with 50 paired samples each after
five warm-ups, show $12.53$--$15.88\times$ host/plain-Python-subprocess runtime.
This is whole-call overhead, not cost added to each syscall. The separately
instrumented operation bodies exclude startup and policy work, but still include
Python wrappers and open/close operations. Appendix~\ref{app:backend-details}
plots every variant and records scope and dispersion. Together, these experiments
show substantial fixed per-call cost on tiny workloads; none supports negligible
enforcement overhead.

\subsection{Supporting reference-monitor evidence}

Historical canaries distinguish call authorization from effects; router analysis
checks 21 dispatch obligations, Tool API conformance covers 15,744 cases, and a
focused router/object/host run passes 151 tests. Appendix~\ref{app:component-evidence}
retains their original snapshots, contracts, static exposure projections, and
open composition findings. These component results do not prove whole-framework
complete mediation or transfer one backend's properties to another.
